# 리캐치 구현 계획 (STEP 1 MVP → STEP 2 실증)

기준 문서: `핀테크_아이디어_공모전_리캐치.hwp` (2026-10). 이 문서는 기획서의 STEP 1·2를 실제로 만들기 위한 준비 사항을 정리합니다.

## 1. 지금 있는 것과 없는 것

| 구분 | 상태 | 위치 |
| --- | --- | --- |
| 웹 시연 (화면 ①~⑪) | 있음. 고정 시연 데이터, 실제 연동 없음 | `index.html` (최신 V6은 PR #1) |
| 바코드 번호 형식 검사 | 있음 (웹 시연은 PR #1, MVP 서버는 같은 규칙 복사본) | `wallet-validation.js`, `mvp/server/barcode-rules.js` |
| 승인 알림 파서 | **새로 만듦** (합성 샘플 기준, 실제 문자로 보정 필요) | `mvp/core/parser.js` |

| Android 앱 (알림 수신·전송, 홈·내역·분석·지갑, 멤버십 바코드, 지갑 편집) | **시제품** (Java, 에뮬레이터 확인 / 실기기 전) | `mvp/android/` |

| 실제 혜택 데이터 (영남대 상권) | 없음. 예시만 | `mvp/data/` |

## 2. 전체 흐름 (2026-10-16 시제품 구조: 파싱은 폰, 계산은 백엔드)

```
카드 승인 문자/앱 푸시
   │  (Android NotificationListenerService, 동의 후 카드 승인·취소로 보이는 알림만)
   ▼
[폰] parser (CardParser.java = core/parser.js) → 금액·가맹점·카드 끝자리·시각·누적 실적만
   │  POST /api/events
   ▼
[백엔드] merchant → engine → matcher (core/*.js) ──추천──► 응답
   │                                                       │
   │                                                       ▼
   │                                 [폰] 알림 "2,509원 더 아낄 수 있어요" → 남은 시간·재결제 방법 화면
   ▼
[백엔드] 이후 취소·재승인 이벤트로 done / pending / missed ... → 월 정산 → (예정) PG 정기결제 청구
```

알림 원문·이름·전체 카드번호는 폰 밖으로 나가지 않습니다. 서버에는 계산·판정에 필요한 카드 끝 4자리와 가맹점명이 저장되며, 이벤트는 24시간 뒤 지웁니다. 실행 방법은 `mvp/README.md`.

## 3. Android 앱

### 권장 구성 (팀 결정 필요)

> 시제품(`mvp/android/`)은 빌드 도구만으로 바로 만들 수 있게 외부 라이브러리 없는 Java로 만들었다. 정식 앱 프레임워크는 아래에서 정한다.

**React Native(Expo dev build 또는 bare) + Kotlin 네이티브 모듈 1개**를 권합니다.

- 코어가 JS라 그대로 단말에서 실행됩니다. 웹 시연 화면도 컴포넌트로 옮기기 쉽습니다.
- 앱이 꺼져 있어도 알림을 처리해야 하므로 Kotlin `NotificationListenerService`가 텍스트를 받아 Headless JS 작업으로 코어를 호출합니다.
- 대안: 순수 Kotlin 앱 + 코어를 Kotlin으로 이식(코어 약 400줄). 이 경우 `mvp/data/notification-samples.json`과 테스트 기대값을 공용 골든 데이터로 써서 두 구현 결과를 맞춥니다.

### 해야 할 일

1. `NotificationListenerService` 모듈: 허용 패키지 목록(카드사 앱, 삼성 메시지·Google 메시지)만 처리하고 나머지는 즉시 버림. `EXTRA_TEXT`/`EXTRA_BIG_TEXT`를 합쳐 코어로 전달 후 메모리에서 폐기.
2. 알림 접근 권한 안내 화면: 무엇을 읽고 무엇을 저장하지 않는지 먼저 보여 주고 동의를 받은 뒤 설정 화면으로 이동 (Play 정책의 '눈에 띄는 공개' 요건).
3. 추천 로컬 알림 + 바코드 화면(남은 시간 카운트다운, 직원 안내 문구, "이미 멤버십 썼어요" 버튼 → `baselineMembershipId`).
4. 지갑 입력: 카드 상품·끝자리·전월 실적·이번 달 사용액, 멤버십·등급. (STEP 3 전까지 수동 입력, 누적 금액이 오는 문자는 자동 갱신)
5. 동의 철회·데이터 삭제 버튼.

### 정책상 주의

- **문자 권한(READ_SMS/RECEIVE_SMS)은 쓰지 않습니다.** Google Play는 기본 문자앱 등 예외 용도에만 허용하므로, 문자앱이 띄운 알림을 알림 접근으로 읽는 방식으로 갑니다.
- Android 13 이상은 APK로 직접 설치한 앱의 알림 접근을 '제한된 설정'으로 막습니다. 베타는 APK 배포 대신 **Play Console 내부 테스트/비공개 테스트 트랙**으로 배포하는 것을 권합니다.
- iOS는 다른 앱 알림을 읽을 수 없으므로 STEP 3(마이데이터 등)까지 미룹니다.

## 4. 서버·정산 (최소한)

- 저장: 사용자 ID, 월별 기록(`toServerRecord` 형식), 동의 이력. 카드·결제 원문 없음.
- 월말 배치: `monthlyStatement()`로 청구액 계산 → PG 정기결제(빌링키) 청구. 자금은 PG가 처리하고 리캐치가 보관하지 않음.
- `pending`(캐시백·청구할인 확정 대기)은 다음 달 명세서에서 확정분만 정산. STEP 1에서는 사용자가 "적립 확인했어요"로 확정하거나, 일정 기간 후 기대값으로 확정하는 정책 중 택1 (아래 5장).
- 기술: README의 FastAPI 또는 NestJS 중 팀 익숙한 쪽. 코어를 서버에서도 쓰려면 Node(NestJS/Fastify)가 유리.

## 6. 데이터 준비 (STEP 1의 실제 병목)

1. **가맹점 목록**: 영남대 정문·경산 상권 카페·외식·편의점·베이커리. 승인 문자에 찍히는 가맹점명을 실제로 모아 `merchants.json` 별칭에 추가.
2. **혜택 룰**: 대학생 보유 비중 높은 카드 10종 내외 + 통신 3사 멤버십 등급별 혜택. 상품설명서·약관 URL과 확인일을 `source`에 남기고 `verified: true`. 전월 실적 산정 제외 항목(상품권·공과금 등)과 통합 월 한도도 확인.
3. **승인 문자 샘플**: 팀원 4명이 보유 카드사별로 승인·취소 문자/푸시를 이름·번호 가려 `notification-samples.json`에 추가 → 파서 회귀 테스트. 카드사 앱 푸시와 문자 형식이 다르므로 둘 다.
4. 웹 시연의 `CAMPUS_POINTS`·지도·사진 교체는 PR #1의 `39nhs _handoff.md` 참고.

## 7. 규제·보안 점검 (출시 전)

- 개인정보: 처리방침, 수집 항목 최소화(이미 코어 구조에 반영), 동의 철회·삭제. 승인 알림은 금융 관련 정보이므로 단말 처리 원칙 유지.
- 전자금융업 등록 필요 여부: PG 정기결제로 수수료만 받고 자금 이동을 중개하지 않는 구조인지 창업보육센터 멘토·법률 자문으로 확인.
- 카드 추천 문구: 특정 카드 **발급 권유**로 보이지 않게 "보유한 카드 중"으로 한정 (여신전문금융업법·금융소비자보호법 모집 행위 해당 여부).
- B2B 리포트: 가명·통계 처리 기준 마련 전까지 수집 데이터 외부 제공 금지.

### STEP 2 지표 (코어 상태값으로 바로 계산)

- 재결제 전환율 = (`done`+`pending`) / 전체 추천
- 1인당 월 순절약액 = `monthlyStatement().net` 평균
- 수수료 결제 수용률 = 청구 성공 / 청구 시도
- 오탐률 = 파싱 실패·가맹점 미식별·잘못된 추천 신고 / 수신 알림 (`ignored`, `unknown_merchant` 집계 + 사용자 신고 버튼)
- 참고: `missed`·`abandoned`·`double_paid` 비율로 2분 안내와 직원 안내 문구 개선
